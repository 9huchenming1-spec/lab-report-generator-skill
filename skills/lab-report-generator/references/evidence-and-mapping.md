# 证据与对应关系

## 最小记录

按题号或原始要求建立条目，不必机械使用 JSON。下面结构展示必须保留的信息：

```json
{
  "id": "任务1",
  "requirement": {"source": "实验说明.pdf", "location": "第2页第1题", "text": "实现排序并处理空输入"},
  "code": [{"source": "src/sort.py", "location": "sort_values，第4至18行", "role": "排序与空输入处理"}],
  "slots": [{"part": "word/document.xml", "path": "/*[1]/*[1]/*[4]", "purpose": "任务1设计思路"}],
  "evidence": [{"kind": "static", "source": "src/sort.py", "location": "第7行", "claim": "空输入返回空列表"}],
  "status": "partial",
  "missing": ["实际运行截图"]
}
```

路径相对本次材料根目录；代码引用应在最终选定版本上核实。不要向公开示例或报告写入本机绝对路径。
完成状态可用 `complete`、`partial`、`missing`、`conflict`，状态由所有要求共同决定，不仅由有没有代码决定。
每个硬性要求和思考题都要有条目。一个条目可引用多个代码位置和模板栏目。

## 证据类型

| 类型 | 来源 | 可支持的表述 |
| --- | --- | --- |
| provided | 用户给出的截图、日志、原始数据 | “所提供的运行记录显示……” |
| executed | 本次可核对的实际执行记录 | “在以下输入下运行，输出为……” |
| static | 源码阅读与控制流分析 | “代码通过……实现……” |
| expected | 基于静态分析的推算 | “根据代码推演，预期输出为……” |
| missing | 没有材料或无法验证 | `【待补充：具体材料】` |

用户口述的环境或结果可记录为 provided，并注明是用户描述。不能自动升级成 executed。
失败运行也是 executed，必须保留错误信息，不能改写为成功。性能、准确率等指标必须有匹配输入和测量方法。
日志与源码版本无法对应时先询问，不能拼成相互支持的结论。

## 运行记录

记录：执行时间、操作系统/解释器或编译器版本、工作目录、源码哈希、命令参数、输入、输出、标准错误、退出码。
原始记录放在工作目录；报告只呈现任务要求和结论所需的部分。不要把个人路径、用户名、令牌等环境细节带入报告。
依赖外部服务、数据库、GUI、硬件或专用工具链的代码，只有获得对应环境和授权才能验证。

## 避免常见误判

- 注释写“支持异常输入”不证明代码实现了异常处理。
- 一个正常输入通过不证明边界条件和全部任务通过。
- “耗时 0.00 秒”不能根据复杂度或主观感觉生成。
- 模板中的示例结果不是本次实验结果。
- 代码缺少功能时，可准确描述现状与原因，但不能替用户完成后假称原答案如此。
