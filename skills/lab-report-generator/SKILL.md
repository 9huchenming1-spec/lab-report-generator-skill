# 实验报告生成

把用户的三类材料连成可核对的报告：**实验要求 → 答案代码 → 模板栏目 → 结果证据**。
内容由模型理解、分析并撰写；脚本只做文档检查、定点填充和格式转换，不是自动判卷器。

## 输入与澄清

先检查已上传附件、当前工作目录和用户消息，识别模板、实验说明、答案代码，以及可选的运行日志、截图和个人信息。
同一文件可能同时含题目和答案，不能只按文件名分类。多个模板或代码版本无法确定时，先询问使用哪一个。

- 模板支持 `.docx` 与 `.doc`；实验说明支持 Word、PDF、图片和文字；代码可为源码文件、文字或项目文件夹。
- 缺少某类关键输入时，集中列出需要补充的材料。不要自行选择网上的通用模板或解答来替代用户材料。
- 模板、题目或代码存在影响内容的歧义、互相冲突的要求或读不清的字段时，先询问，等待相关答案再处理该部分；继续做不依赖答案的工作。
- 姓名、学号、班级、日期、环境信息等不自行猜测。缺少且不影响分析时可先写 `【待补充：字段】`，交付时列出。
- 用户的直接说明优先。实验要求决定必须回答什么，模板决定结构和版式，代码及结果证据决定实际完成了什么。三者冲突不能用优先级掩盖，应说明冲突并询问。

## 1 分析模板

读取 [文档处理](references/document-handling.md)。保留输入原件，记录哈希并在独立工作目录操作。
`.doc` 通过转换工具生成 `.docx` 工作副本，不能改扩展名冒充转换；转换后需核对原件的页面、表格和栏目。

对 DOCX 运行 `scripts/docx_template.py inspect`，并用可用的渲染工具查看模板各页。
识别封面、章节顺序、逐题栏目、说明文字、示例答案、表格和合并单元格、页眉页脚、分页及样式。
正文段落不是完整文档：也要检查表格、文本框、内容控件、页眉页脚和已有图片。

在工作目录记一份简短的模板合同：原件路径和哈希、页面和字体规则、保留内容、可填写位置、允许扩展的版式，以及修改位置的稳定定位符。
没有占位符的模板同样支持：根据栏目语义定位空段落或表格单元格，填写前验证该位置的原文。
无法确定哪个区域可改时询问；不要仅凭空白位置自动写入。

## 2 分析实验要求

完整读取实验说明，按原编号逐项提取实验目的、任务、输入输出、方法约束、边界条件、截图/数据要求、思考题和提交要求。
保留评分点、字数限制和指定环境，不将一般建议误当成硬性要求。
PDF 保留页码；图片及扫描页通过视觉识别，读不清处请求确认，不能把提取不到文字当作没有要求。

## 3 分析答案代码

读取 [证据与对应关系](references/evidence-and-mapping.md)。先静态分析代码的入口、模块、数据流、算法、依赖与输入输出，再逐题对应实验要求。
不按编程语言限制分析；代码语言和项目规模决定阅读方式。对项目先找入口和调用关系，避免只读一个文件。
识别未实现的任务、与题意不符的行为、可能的错误和不能验证的内容。解释用户实际代码，不将理想解法写成已完成实现。
用户仅要求生成报告时，不擅自修复源码；将影响结论的问题说明并询问是否修复。

只有在确有必要、环境具备且现有授权覆盖时运行代码。先检查文件、网络、设备和依赖副作用；需要安装依赖、接触外部系统或执行有风险操作时先询问。
运行使用工作副本和明确的时间限制，记录命令、版本、输入、标准输出、错误及退出码。示例小程序的成功不代表整个项目通过。
缺少运行环境不阻止静态分析，但相关部分只能标记为预期或待补充，不能声称测试通过。

## 4 建立对应关系并撰写

在工作目录建立简洁的逐项映射，格式见 [证据与对应关系](references/evidence-and-mapping.md)。每道题均记录要求来源、代码位置、模板位置、结果证据和完成状态。
共享代码可以对应多项要求；缺少代码的题目也要保留条目并标记缺口。

按模板栏目组织正文，而不是固定添加“目的、原理、步骤、总结”全套标题。
需要时撰写目的、原理、设计思路、关键代码、实验步骤、结果分析、思考题及总结；深度和篇幅跟随实验要求与可用证据。
代码片段来自用户源码，保持标识符及语义一致。题目要求完整代码时不要只提供片段。
分析要解释代码为什么产生该结果、是否满足要求、存在什么限制，避免空泛的“达到了实验目的”。

- 用户提供的截图或日志：注明来自用户材料，不声称本次亲自复现。
- 本次实际运行：有命令、输入、输出和退出码支持后，才写“运行结果”。
- 静态分析或推演：用“根据代码分析”“预期输出”等措辞；推算的数据不能冒充测量值。
- 缺少证据：写 `【待补充：实际运行结果/截图/数据】`，集中告知用户。
- 不生成伪终端截图、不杜撰运行时长或设备配置、不虚构调试经历与个人感想。

结果和总结应如实描述代码完成度；明显错误未解决时不能写“全部满足要求”。

## 5 填充并验证文档

以模板副本为基础写入。`scripts/docx_template.py fill` 支持已确认的纯文本位置与跨 run 的文字替换，并强制检查模板哈希和位置原文。
脚本不能代替内容分析，也不处理图片插入、扩展表格、复杂控件或公式；遇到这些任务，按 [文档处理](references/document-handling.md) 使用合适的文档工具，在副本中局部修改并核对保留项。
不将全文拼成新文档来声称保留了模板，不用统一字体或缩小全文来掩盖溢出。

读取 [交付检查](references/quality-checklist.md)，检查两类问题：

1. 内容：每项要求与思考题都有回应；事实与代码及证据一致；占位符和待补充项已识别；格式说明与示例答案没有误入正文。
2. 文档：渲染最终 DOCX 并逐页查看，检查文字裁切、表格溢出、分页、字体、图片、页码、页眉页脚；对比模板合同及未修改包部件。

需要 PDF 时，用 `scripts/convert_document.py` 从最终 DOCX 导出并逐页检查；不把另一份独立生成的 PDF 当作同一报告的导出。
缺少转换器、字体、渲染器或视觉查看能力时，先解释具体限制并询问用户如何继续；不能称为“已完成视觉验证”。
有待补充内容只能交付明确标注的草稿；用户补齐材料后再完成对应内容和必要的版式复验。

## 交付

默认仅返回报告 DOCX 的可点击文件链接，以及影响使用的待补充项或已知限制；用户要求时另附 PDF。
输入原件保持不变。中间提取文本、对应表、日志和渲染图留在工作目录，除非用户要求，不作为报告正文或额外交付物。
生成实验报告不包含上传 GitHub、提交课程系统或对外发送；这些操作需要用户另行明确要求。
